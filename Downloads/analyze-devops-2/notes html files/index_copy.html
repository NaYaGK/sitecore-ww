🧠 Core Concepts — The Why Behind Every Command

🗂

Filesystem Hierarchy Standard

Linux organises everything under / (root). Every file, device, and process is a path. There are no drive letters like Windows.

Analogy: Think of / like the ground floor of a building. /home is the residents' floor. /etc is the manager's office with config files. /var is the storage room with logs and data.

🔐

File Permissions (rwx)

Every file has 3 permission sets: owner, group, others. r=read(4), w=write(2), x=execute(1). These numbers add up: 755 = owner full, group+others read+execute.

Analogy: Your front door key (owner), spare key for family (group), and the fact a stranger can ring the bell but not enter (others).

⚙️

Processes and Services

Every running program is a process with a PID (process ID). systemd manages services — programs that start at boot and run in the background (like nginx, sshd).

Analogy: A process is like a running app on your phone. A service is like an app set to auto-start when you turn the phone on.

📦

Package Manager (apt)

apt is Ubuntu's app store for the terminal. apt install downloads and installs software. apt update fetches the latest list of available software — do this before every install.

Analogy: apt update = refreshing your app store. apt install nginx = downloading and installing the app.

📝

Text Editors: nano vs vim

On a server you have no GUI. You edit files in the terminal. nano is beginner-friendly. vim is what seniors use. Learn nano first — know that vim exists.

Analogy: nano is like Notepad. vim is like a professional IDE but keyboard-only — has modes that confuse beginners.

🔌

SSH (Secure Shell)

SSH is how you connect to a remote server (like your EC2) from your laptop. You use a private key (.pem file) instead of a password. The server has the matching public key.

Analogy: A lock-and-key system. Your .pem file is the physical key. The EC2 is the lock. Only your key opens it.

SESSION 3 of 4 — Permissions + Users + Services
Understanding and Changing Permissions
$ ls -la day1.txt
-rw-rw-r-- 1 ubuntu ubuntu 35 Jun 2 10:30 day1.txt
# Breakdown: - (file) rw- (owner: read+write) rw- (group: rw) r-- (others: read only)
$ chmod 755 day1.txt
$ ls -la day1.txt
-rwxr-xr-x 1 ubuntu ubuntu 35 Jun 2 10:30 day1.txt
# 7=rwx (owner), 5=r-x (group), 5=r-x (others)
$ chmod 600 day1.txt # Owner read+write only, nobody else
$ chmod +x myscript.sh # Add execute permission (symbolic method)
$ chown root:root day1.txt # Change owner to root
chown: changing ownership of 'day1.txt': Operation not permitted
# You need sudo (superuser do) for that. This is correct behavior.
$ sudo chown ubuntu:ubuntu day1.txt # sudo grants temporary root powers

🐛 Debugging Flow — Day 1 Most Common Failures

⚡ If SSH Connection Fails

1
Check error message first "Permission denied (publickey)" → key problem. "Connection timed out" → network/security group problem.
2
Key permissions wrong (most common) AWS refuses connection if .pem is readable by others. chmod 400 your-key.pem
3
Wrong username — Ubuntu EC2 uses "ubuntu", not "ec2-user" Amazon Linux uses ec2-user. Ubuntu AMI uses ubuntu. Check which you launched. ssh -i key.pem ubuntu@IP
4
Security Group blocking port 22 Go to EC2 console → Security Groups → Inbound Rules. Port 22 must allow your IP (or 0.0.0.0/0 for testing, never in production).
5
Instance is stopped Check EC2 console. Instance State must be "Running". Start it if stopped.

⚡ If a Command Says "Permission denied"

1
Try running with sudo first sudo [your command here]
2
Check file ownership Who owns the file? Who are you? ls -la filename && whoami
3
Check if execute bit is missing for a script chmod +x script.sh && ./script.sh

💥 Common Beginner Mistakes — Day 1

⚠ Mistakes Senior Engineers See Every Week From Beginners
✗
Using sudo for everything Running all commands as root because "it avoids permission errors." This destroys proper file ownership and creates real security risks in production. Use sudo only when explicitly needed. ✓ Fix: Run as ubuntu, escalate to sudo only when the command itself requires it.
✗
Using > when they mean >> echo "line" > file.txt overwrites the entire file every time. Beginners lose data they wanted to keep. ✓ Fix: Use >> to append. Use > only when you want to replace the entire file content.
✗
Not updating before apt install apt install nginx without running apt update first installs old or wrong versions from a stale package list. ✓ Fix: Always: sudo apt update && sudo apt install [package] -y
✗
Leaving EC2 running when not studying Free tier has limits. Leaving a t2.micro running for 31 days is fine. Leaving 2–3 running or running larger instances drains your free tier allowance and causes unexpected charges. ✓ Fix: Stop (not terminate) EC2 when done for the day. Stop = paused, billed for storage only. Terminate = permanently deleted.
✗
Pasting commands without reading them Copying a Stack Overflow command and running it blindly. In DevOps this causes real outages. In learning it means you understand nothing. ✓ Fix: Read every command word by word. Look up any flag you don't know with man [command] or [command] --help.
✗
Treating chmod 777 as the fix-everything command chmod 777 gives everyone read+write+execute access to a file. Beginners use it to fix permission errors. In production it's a critical security vulnerability. ✓ Fix: Diagnose why you need access (wrong user? wrong group?), fix the root cause. chmod 777 is almost never the right answer.

🎤 Interview Explanation Prompts — Day 1 Topics

Practise saying these out loud. Recruiter phone screens often start with "can you explain..."

INT Q → "Can you explain Linux file permissions to me?"
Your answer structure: "Linux permissions are split into three groups: the owner of the file, the group it belongs to, and everyone else — called others. Each group gets three bits: read, write, and execute, represented as rwx. These map to numbers: r=4, w=2, x=1, so 7 means full access, 5 means read and execute, 4 means read only. A permission of 755 means the owner has full access, and the group and others can read and execute but not write. chmod is the command to change permissions, chown changes ownership. I use chmod 600 for private key files — only the owner can read, nobody else can touch it."
INT Q → "What's the difference between a process and a service?"
Your answer structure: "A process is any running program — it has a Process ID, uses CPU and memory, and ends when its job is done. A service is a special type of process managed by systemd — it's designed to start at boot time, run continuously in the background, and be monitored and restarted if it crashes. For example, when I install nginx on a server, I use systemctl enable nginx to make it a service that starts automatically on every reboot, rather than having to manually start it each time."
INT Q → "Why would you use sudo and when wouldn't you?"
Your answer structure: "sudo — superuser do — temporarily elevates your privileges to root level for a single command. I use it when I need to install packages, modify system configuration files in /etc, or manage services with systemctl. I would not use it for anything involving my own files in my home directory, or when writing application code. Running everything as root is dangerous because a bug or mistyped command has system-wide consequences — there's no safety net."

🧪 Day 1 Quiz — Test Yourself Before Moving On

⚡ Day 1 Knowledge Check — Pass = 4/5 correct
Q1. What does chmod 644 notes.txt mean?
A) Owner, group, others all have read+write access
B) Owner has read+write; group and others have read-only
C) Everyone has full access
D) Owner has execute; group has write
6=rw (4+2), 4=r (read only). So owner gets read+write, group gets read, others get read. Perfect for a public config file — everyone can read it, only you can edit it.
Q2. You want to append a line to a file without deleting its contents. Which operator?
A) >
B) >>
C) |
D) &
> overwrites. >> appends. | pipes. This is one of the most common beginner mistakes that causes data loss.
Q3. A service file change isn't taking effect after editing it. What are the correct two commands to apply the change?
A) sudo reboot && sudo apt update
B) sudo service reload && sudo restart
C) sudo systemctl daemon-reload && sudo systemctl restart [service]
D) sudo kill [pid] && sudo start [service]
After editing a systemd service file you must daemon-reload (re-read the config) then restart the specific service. Rebooting the whole server is amateur behaviour in production.
Q4. Where would you look for nginx error logs on a Linux server?
A) /home/ubuntu/logs/
B) /etc/nginx/errors/
C) /var/log/nginx/
D) /tmp/nginx/
/var is for variable data — logs live at /var/log/. Application logs (nginx, apache, etc.) almost always live here. Learning to read logs is 50% of being a DevOps engineer.
Q5. What command shows all currently running processes including their CPU and memory usage, live?
A) ps aux
B) df -h
C) top or htop
D) who
ps aux gives a snapshot. top and htop are live/real-time views that update every second. htop has a better interface and is preferred by most engineers.

🧠 Core Concepts

🌿

Git Three-Area Model

Working Directory: files you're editing. Staging Area (index): changes marked ready to commit. Repository (.git): permanent history of commits.

Analogy: Working dir = shopping basket. Staging = items at the checkout belt. Repository = receipt/purchase history.

🔗

Remote vs Local Repository

Local repo lives on your machine (or EC2). Remote repo lives on GitHub/GitLab. git push sends local → remote. git pull brings remote → local.

Analogy: Local repo = your personal notebook. GitHub = the cloud-backed shared copy your whole team can read.

🪪

IAM — Identity and Access Management

AWS root account = god mode. Never use it for daily work. IAM lets you create users with specific permissions. Every person, application, or EC2 that touches AWS needs an IAM identity.

Analogy: Root is the master key to the building. IAM users are individual keycards with specific room access.

⌨️

AWS CLI

The AWS web console is a GUI for learning. Real DevOps uses the CLI or infrastructure-as-code. aws configure sets up your access keys. Then you can control EC2, S3, IAM from the terminal.

Analogy: Console = ATM touchscreen. CLI = talking directly to the bank system. Faster, scriptable, auditable.

🎤 Interview Explanation Prompts — Day 2 Topics

INT Q → "Walk me through the git workflow — what happens when you make a change?"
Your answer: "Git has three areas. The working directory is where you edit files. When a change is ready to be saved, I stage it with git add — this moves it to the staging area, also called the index. I then run git commit with a meaningful message, which permanently records that snapshot in the local repository. If I'm working with a team, I push to the remote — GitHub in most cases — using git push. Git pull brings other people's changes down to my local copy. INT Q → "Why does AWS have IAM and why shouldn't you use the root account?"
Your answer: "The root account in AWS is the original account owner and has unrestricted access to everything — all services, all regions, all billing. IAM — Identity and Access Management — lets you create separate users and roles with only the permissions they actually need. This follows the principle of least privilege. If an IAM user's credentials are compromised, the damage is limited to what that user can do. If root credentials are compromised, an attacker has full control of your entire AWS account. In practice: I enable MFA on root, lock the root credentials away, and create an IAM user with AdministratorAccess for my daily work. In a company, individual team members would have even more restricted IAM roles — a developer might only be able to write to S3 and trigger Lambda, not touch EC2 or billing."

🧠 Core Concepts

🌐

Security Groups — The First Debugging Stop

A security group is EC2's firewall. It controls which traffic can reach your instance. Inbound rules = who can connect to you. Outbound rules = what your instance can connect to. By default: only port 22 (SSH) is open.

Analogy: A building's door security list. Port 22 (SSH) = staff entrance. Port 80 (HTTP) = public entrance. If you forget to open port 80, no browser can reach your web server — and that's the #1 mistake on Day 3.

🏷

Public IP vs Elastic IP

When you stop and start an EC2, the public IP changes. An Elastic IP is a static IP that stays assigned to your instance. For learning, the dynamic public IP is fine. For production, you'd use an Elastic IP or a load balancer DNS name.

Analogy: Dynamic IP = a rental car that's a different car every morning. Elastic IP = your own car with a fixed number plate.

🔄

User Data — EC2 Launch Scripts

You can pass a shell script to EC2 at launch time. It runs as root the very first boot. This is how DevOps engineers automate server setup — no manual SSHing and installing. This is the seed of configuration management.

Analogy: Like writing instructions on a sticky note that the server reads and executes the moment it wakes up for the first time.

🕸

Nginx — What a Web Server Does

Nginx is a web server. It listens on port 80 (HTTP) or 443 (HTTPS). When a browser requests your IP, nginx receives the request, finds the right HTML file, and sends it back. Config lives at /etc/nginx/sites-available/.

Analogy: A restaurant host. The browser is the customer. Nginx is the host who greets them, checks which table (URL path) they want, and delivers the right dish (HTML file).

🐛 The Most Important Debug Tree — Nginx Not Loading in Browser

🔴 "This site can't be reached" — Systematic Approach

Do not guess. Do not Google first. Work through this tree top to bottom. One of these will find your problem 95% of the time.

⚡ Nginx Not Serving in Browser — Full Debug Flow

1
Check if nginx is actually running The most common cause. The service stopped or was never started. sudo systemctl status nginx If "inactive (dead)" → start it. If "failed" → check logs.
2
Check Security Group allows port 80 Second most common cause. You might have only opened port 22. aws ec2 describe-security-groups --group-ids sg-YOUR_ID Look for IpPermissions with FromPort:80. If not there, add the inbound rule.
3
Test from inside the server first Isolates whether it's nginx or network. curl http://localhost If this works but browser doesn't → Security Group problem. If this fails too → nginx problem.
4
Check nginx error logs Always look at logs when something fails. This is the universal debugging principle. sudo tail -50 /var/log/nginx/error.log
5
Check nginx config is valid A syntax error silently breaks nginx on reload. sudo nginx -t
6
Check if something else is using port 80 Apache might be installed alongside nginx, or another service grabbed the port. sudo ss -tlnp | grep :80
7
Verify EC2 public IP is correct If you stopped and restarted, the IP changed. aws ec2 describe-instances --query 'Reservations[0].Instances[0].PublicIpAddress' --output text

Q1. Your web page is not loading in the browser. nginx status shows "active (running)". What is the FIRST thing you check next?
A) Check if the HTML file exists
B) Check if the Security Group has port 80 open for inbound traffic
C) Restart the EC2 instance

If nginx is running but the browser can't reach it, it's almost always the Security Group. Port 80 must have an inbound rule. Run: aws ec2 describe-security-groups and check IpPermissions for port 80.
Q2. What is the difference between systemctl restart and systemctl reload for nginx?
A) They do the same thing — both restart the process
B) restart stops and starts nginx (drops connections); reload applies new config without stopping (zero downtime)
C) reload is only for security updates
D) restart is faster than reload
reload = graceful config update. Active connections finish normally while new config is applied. Always prefer reload for config changes in production. Use restart only when reload fails or for major version upgrades.
Q3. You edited nginx.conf and ran sudo systemctl reload nginx but the site broke. What should you have done BEFORE the reload?
A) Backed up the config file
B) Run sudo nginx -t to test config syntax
C) Rebooted the server first
D) Checked the security group
sudo nginx -t validates config syntax without touching the running nginx. If it reports an error, the file has a problem. Never reload nginx without testing first — a bad config can take the site down immediately.
Q4. Inside your deploy.sh you want to check if a directory exists before cloning. Which bash check is correct?
A) if exists "$DIR"; then
B) if [ -d "$DIR" ]; then
C) if directory "$DIR"; then
D) if file "$DIR"; then
-d tests for directory. -f tests for file. -e tests for either. [ -d "$DIR" ] is the correct bash syntax for directory existence check. Always quote variables in bash — unquoted paths with spaces break scripts.
Q5. Where does nginx serve files from by default?
A) /home/ubuntu/www/
B) /etc/nginx/html/
C) /var/www/html/
D) /usr/share/nginx/
/var/www/html/ is the default nginx web root on Ubuntu. The config at /etc/nginx/sites-available/default points to this path. When you replace index.html here, nginx serves your file immediately after reload.
